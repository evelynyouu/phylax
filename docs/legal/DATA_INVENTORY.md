# Phylax data inventory

Built from the code on branch `supabase-accounts`. Line numbers refer to the files as read on 2026-11-11 around 00:50; another agent was editing code at the same time, so recheck them. "App-encrypted" means Phylax encrypts the value itself before saving it; Supabase separately states that all customer data is encrypted at rest with AES-256 and in transit with TLS ([Supabase security](https://supabase.com/security)).

Access legend:
- **User** = the signed-in owner, through row level security (RLS) policies `*_owner` (`supabase/migrations/20261110000000_init.sql:47-87`).
- **Server** = Phylax server code acting for the signed-in user (anon key plus the user's session, so RLS applies) (`lib/store/index.ts:11-14`, `lib/supabase/server.ts`).
- **Admin** = anyone holding `SUPABASE_SERVICE_ROLE_KEY` (bypasses RLS). Used by account deletion (`app/api/account/delete/route.ts`) and the eval export script (`scripts/eval-export.ts`), which only runs for `EVAL_OWNER_USER_ID`, the developer's own account.
- **Dev** = the developer, through the Supabase and Vercel dashboards.

| Account emails (sign-up confirmation) | Supabase default SMTP, or a custom SMTP provider | Only if email confirmation is on. Logging check: deployed code logs only through `logError` in `lib/log.ts`, which writes a label, the error's message (capped at 300 characters) and a short code, never the error object. Google client (gaxios) errors carry the request config including the `Authorization` header, so the object itself is never logged. Callers: `app/api/sync/route.ts` and `app/api/account/delete/route.ts`. No email subject, sender or body is logged. All other logging is in `scripts/`, which are local developer tools.

## 4. What deletion actually removes

| Action | Removes | Leaves |
|---|---|---|
| Disconnect Gmail (`app/api/auth/disconnect/route.ts`) | Google grant (best effort; the response says `revokeFailed: true` when Google did not confirm, `lib/gmail.ts` `revokeBestEffort`); `gmail_connections` row | All `records` and marks; the Google grant itself if revocation failed (the user can remove it at https://myaccount.google.com/permissions; the UI does not show this yet) |
| Delete account (`app/api/account/delete/route.ts`) | `auth.users` row (hard delete, done before the Gmail grant is revoked and after the photo call below: if it fails nothing else changes and the Gmail connection stays); cascades to `records`, `gmail_connections`, `dismissed`, `manual_cancels`, `paid`, `reminders`, `merchant_categories` (database tables, all `on delete cascade`, migration `:5-41`). The profile photo is not a database row and does not cascade: just before the account is deleted, an explicit storage call removes `<user id>/avatar` from the `avatars` bucket (best effort; if it throws, the error is logged and deletion continues); session cookies; then, only after the delete succeeded, the Google grant (best effort, revoked from the tokens read beforehand; `revokeFailed: true` in the response if Google did not confirm) | Browser `localStorage` item; the Google grant if revocation failed; Vercel and Supabase logs until they expire; Supabase auth audit entries (unverified); any local eval corpus that includes the user; a profile photo whose removal failed may remain in storage |
| Supabase backups | Free plan: Supabase documents daily backups only for Pro, Team and Enterprise ([Supabase backups](https://supabase.com/docs/guides/platform/backups)). Whether any internal backup exists on the free plan is unverified. | |
